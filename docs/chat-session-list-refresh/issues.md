# 聊天列表去网页感改造问题记录

## 当前已知问题

- 当前会话列表宽度偏大，像内容栏，不像工具轨
- 当前头像是高饱和渐变圆球，AI 产品味明显
- 当前每行时间、删除按钮和会话卡片层级同时存在，信息密度偏高
- 当前搜索框过厚，像表单控件，不像轻筛选器
- 当前本地 pane 标题和双行列表会持续把会话区拉回“网页内容栏”心智
- 当前聊天路由存在独立的全局业务 rail，这会持续把聊天空间拉回“后台导航”心智；仅靠调色和 hover 无法根治
- 新建会话这条链曾出现“局部模块已修、真实 store 未修”的漂移，导致 `/new`、排序和 Agent 选择表面存在、实际闭环不完整
- 运行时 `sessions.list` 会返回 `:cron:` 与 `:subagent:` 这类内部会话；如果只在 UI 层隐藏，首屏选中和排序仍会被它们污染
- `chat.ts` 与 `session-actions.ts` 之前长期各自维护一份 `sessions.list` 规范化逻辑，是这条链反复漂移的结构性原因

## 设计取舍

- 不直接照抄 QClaw 的弹层搜索，因为 XClaw 目前 inline 搜索更高效
- 不完全取消多 Agent 区分，但默认不再常驻副标题/身份章
- 不继续保留每行时间；如果后续实测损伤定位效率，再回头评估更轻的时间表达
- “本周”当前按本地周一作为起点，这轮先固定，不继续扩成用户可配置口径
- 共享身份章允许继续保留给聊天正文；但聊天列表默认不再显示身份章

## 开发准则补充

- 小改动可以敏捷直改，但前提是必须先确认风险边界，不得靠猜测补样式
- 任何“参考 QClaw”的改动，都必须先确认 XClaw 本地确实存在对应问题，否则不做
- 参考外部产品时，优先吸收交互逻辑和层级原则，不照搬像素皮
- 文档、i18n、测试三层必须和实现同步收口；不能只改组件，再靠“本地看起来差不多”收尾
- 涉及 store 拆分或旁路模块时，必须先确认应用真实入口实际依赖哪条实现链，禁止只修未接入的模块后就宣称闭环
- 会话列表的“去噪”不能只停在组件层；只要影响首屏选中、排序或当前会话推断，就必须下沉到 store/数据规范化层
- 同一条会话语义如果在 `chat.ts` 和 `session-actions.ts` 各维护一份实现，必须优先抽共享 helper，而不是继续双改双测

## 待观察项

- 去掉每行时间后，用户是否会觉得会话定位效率下降
- 默认单行文本后，多 Agent 辨识度是否依然足够
- 搜索框是否还需要进一步收成更接近 trigger 的轻入口
- 工作区入口折回聊天侧栏底部后，是否还需要进一步压缩或重排 utility 区
- 是否还存在其他自动化会话 key 形态需要从主会话轨排除，目前已确认 `:cron:`、`:subagent:`，`telegram/wecom` 等真实渠道会话应保留
