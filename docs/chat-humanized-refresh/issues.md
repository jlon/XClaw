# 聊天区域人性化设计优化问题清单

## 已确认问题

1. 当前聊天区仍有明显的网页组件堆叠感，主观上不够像桌面工作区。
2. 快捷操作已经存在，但入口层级和默认存在感仍不够自然。
3. `thinking / tool / status / error` 各自成立，但没有形成统一的过程语义。
4. 如果继续只做单点微调，聊天区域会越来越碎，最终变成大量 patch。

## 本轮已收问题

1. 连续 assistant 输出、过程轨和 loading 行重复抬起身份头像的问题已经收掉。
2. 所有消息一律使用同一个大段距的问题已经收掉，连续 assistant 输出现在会保持更紧的阅读节奏。
3. 欢迎态过于接近 landing hero 的问题已经继续压回桌面启动工作区。

## 第二阶段接受的取舍

1. 不追求一次性把所有交互都做满。
2. 不引入需要 runtime 新数据支持的功能。
3. 只保留真实高频动作，不做功能炫技。

## 风险点

1. 人性化改造如果越界到消息结构，容易破坏第一阶段刚修好的滚动链。
2. 过度学习 `QClaw` 容易把 `XClaw` 做成样式模仿，而不是产品优化。
3. 如果把快捷操作做得过强，会重新放大 AI 控制台感。
4. 如果误把 `QClaw` 的“次级动作默认接近隐身”理解成“直接删掉元信息和复制入口”，会损失可发现性，这不是它真正的设计逻辑。
5. 聊天主区、侧栏和 composer 的明暗关系已经开始向 `QClaw` 靠拢，但在极亮、极暖、低对比壁纸下仍需继续做真实窗口抽样，不可以只看静态截图。
6. `QClaw` 的主区更亮，不代表 `XClaw` 可以长出局部白卡；一旦把阅读层重新做成独立矩形，壁纸连续性就会被破坏。

## 开发准则补充

1. 学 `QClaw` 时优先学产品逻辑和交互层级，不学像素皮。
2. 第二阶段任何新增快捷操作，都必须回答两个问题：
   - 当前 `XClaw` 是否已有真实使用价值？
   - 是否不需要新增协议和状态链就能闭环？
3. 如果一个操作默认常驻会打断正文阅读，它就应该改成 hover、异常态、或空态增强，而不是一直显示。
4. `QClaw` 的直接证据表明：
   - 用户消息可以有更明确的输入感
   - 助手消息应保持更像文稿流
   - 次级动作应后置、弱默认态、hover 才增强
   这三点可以学，但不能照搬它的主题皮和分组协议。
5. 连续 assistant 输出的身份弱化只在本地确实出现阅读噪音时才做，不为了“像 QClaw”而强行分组。

## 后续跟进项

1. 第二阶段结束后，再评估是否需要 follow-up 建议或 hook 动作系统。
2. 如果要做消息级重试，必须先补真实请求级上下文，不能做假按钮。
3. 仍需保留真实 `dev` 环境手工验收，不允许只看组件级快照。
4. 继续验证有壁纸和无壁纸两种状态下，主区始终略亮于侧栏，且 composer 不重新抬成独立控制台。
