# 聊天性能与流畅度优化问题清单

## 已确认问题

1. 聊天消息仍是全量富内容渲染，长会话下首屏与滚动成本过高。
2. 首次进入聊天和切换会话时，滚动初始化策略过重，会放大空白和跳动感。
3. 消息列宽规则不统一，正文、meta、复制、thinking、tool、附件容易出现错位。
4. 当前聊天主区仍保留较多网页组件式的厚视觉层，会放大“不流畅”的主观感受。

## 第一阶段接受的取舍

1. 不在第一阶段引入虚拟列表。
2. 不重写消息协议和 store。
3. 允许为了稳定滚动体验，降低部分富内容的默认存在感。

## 风险点

1. 改动消息结构后，复制、时间、thinking、tool 状态可能出现回归。
2. 改动滚动初始化后，流式输出、切换会话、回到底部可能出现行为变化。
3. 如果只收样式不收结构，用户当前反馈的问题不会真正消失。

## 开发准则补充

1. 对齐 `QClaw` 前，必须先在本地 `XClaw` 拿到真实问题证据，禁止无证据照搬。
2. 聊天优化必须以完整链路验证为准，不能只修局部样式后就宣称闭环。
3. 如果问题同时涉及布局、滚动和富内容渲染，优先怀疑结构设计，而不是先堆补丁。
4. 小的、低风险、局部 UI 微交互改动允许敏捷直改，不强制要求红绿测试；但前提是不能影响协议、状态链、滚动契约和跨组件数据流，并且仍需做最小静态校验或直接目视验证。

## 后续跟进项

1. 第一阶段完成后再评估是否需要“长会话轻虚拟化”。
2. 如果滚动仍不稳，再单独评估 `ResizeObserver + 高度契约` 的第二阶段方案。
3. 需要在真实 `dev` 环境对用户截断截图对应路径做手工确认，不能只以源码测试替代。
4. 不再对整条消息行使用 `content-visibility`，后续只允许在次级重块上使用，避免长消息滚动跳变。
5. 需要补一轮 review，确认 `content-visibility` 不会对 streaming、lightbox 和复制 hover 行为造成副作用。
