# 技能中心 QClaw 桌面化对齐设计

## 背景

当前 `XClaw` 的技能页更像后台管理页，而不是桌面应用里的技能中心：

1. 主视图承担了搜索、筛选、安装、配置、目录操作、环境变量、API key 等过多职责。
2. 右侧厚详情抽屉和配置表单抢走了视觉重心。
3. 本地技能、安装来源、外部发现被混在一层，页面心智不稳定。

本轮对齐目标必须以**本机安装版 QClaw 的技能管理中心**为准，而不是 `OpenClaw` 上游源码里的分组列表页。当前可确认的证据包括：

1. 用户提供的本机 QClaw 截图：`技能管理`、`搜索已经安装的技能`、`添加技能`、双列卡片、开关、`内置技能` 标签。
2. 本地解包资源：`/tmp/qclaw-asar-fgpUo0/out/renderer/assets/c-8d_bn_BT.js`
3. 解包字符串已确认存在：
   - `技能管理`
   - `搜索已经安装的技能`
   - `添加技能`
   - `内置技能`
4. 三次子代理 review 的共同结论：
   - 主搜索应是本地已安装技能搜索，不应直接变成跨 provider 商店搜索。
   - 页面主结构应是单一技能卡片网格，不应再拆成多分组工作台。
   - 二级层应是轻量详情弹窗，不应继续沿用重后台抽屉。

## 目标

1. 主信息架构、操作层级和视觉密度全面对齐 QClaw 技能管理中心。
2. 保持桌面级 `macOS / Windows` 质感，不做网页商店感。
3. 让主页面只承担“浏览、搜索本地技能、启停、进入次级动作”。
4. 保留 `XClaw` 现有深度能力，但全部下沉到次级层。
5. 支持 `ClawHub` 与 `腾讯 SkillHub` 的搜索与安装，但它们必须进入“添加技能”的次级流，而不是污染主技能中心。
6. 安装仍然走“跳到聊天窗口 + 自然语言安装”的用户体验，但底层执行不能依赖纯模型臆断，必须挂在可靠的 provider adapter / host action 上。

## 非目标

1. 不对齐 `OpenClaw` 上游 `skills.ts` 的 grouped workbench。
2. 不把主页面做成多来源 marketplace 首页。
3. 不把 `ClawHub`、`SkillHub` 搜索结果直接混到本地技能主网格。
4. 不在主层继续暴露 API key、环境变量、路径、README、卸载等重管理能力。
5. 不为了表面对齐而使用错误的来源语义，例如继续拿 `bundled` 冒充 `XClaw 自带`。

## 核心设计结论

### 1. 主页面只展示本地技能中心

主页面的搜索对象只能是**本地已存在的技能**，包括：

1. `XClaw` 预装技能
2. 用户通过 `ClawHub` 或其他方式安装到本地的技能
3. 工作区技能
4. 额外目录技能
5. `.agents` 侧技能

这层不承载外部 catalog 搜索结果。

### 2. 外部发现下沉到“添加技能”

`添加技能` 按钮打开二级菜单，而不是直接在主页面展开安装 sheet。当前菜单只保留三个实际有价值的入口：

1. `从 GitHub 导入`
2. `从 ClawHub 搜索`
3. `从 SkillHub 搜索`

不再保留“通过对话创建”这条入口。原因很直接：它会把技能中心重新带回泛聊天入口，弱化当前页面作为桌面技能管理中心的角色。

### 3. 主页面是单一网格，不做多分组主视图

QClaw 证据更接近“单一 skill grid + 每卡标签”，而不是“按来源拆出多块区域”。因此：

1. 主体是一个统一的技能卡片网格。
2. 不默认展示 `内置技能 / 已安装技能 / 工作区技能 / 额外目录` 四大分组块。
3. 来源通过卡片底部轻标签表达，不通过版块切分。
4. 排序可以优先 `XClaw 预装`、再到已启用、本地用户技能、其他来源，但视觉上仍是一体的网格。

## 来源语义与数据判定

这是本轮必须纠正的关键点。

### 当前事实

1. `electron/utils/skill-config.ts` 中的 `BUILTIN_SKILLS` 当前为空。
2. 真正随 `XClaw` 一起提供的是 `resources/skills/preinstalled-manifest.json` 中声明并由 `ensurePreinstalledSkillsInstalled()` 部署的预装技能。
3. 每个由 `XClaw` 预装部署的技能目录会写入 `.XClaw-preinstalled.json` 标记文件。
4. 现有前端/host 数据链路没有把这个 provenance 暴露给 `Skills` 页面。

### 正确结论

1. 页面上的“内置技能”文案如果继续保留，只能建立在 `xclaw-preinstalled` 这一产品级来源字段上。
2. 不能再拿 `bundled`、`always` 或 `openclaw-bundled` 去冒充 `XClaw 自带技能`。

### 正确实现原则

技能数据需要在 host/main 层合并出统一 provenance，再提供给前端。至少包含：

1. `xclaw-preinstalled`
2. `openclaw-managed`
3. `openclaw-workspace`
4. `openclaw-extra`
5. `agents-personal`
6. `agents-project`
7. `openclaw-bundled`
8. `unknown`

其中 `xclaw-preinstalled` 的判定证据必须来自：

1. `resources/skills/preinstalled-manifest.json`
2. 技能目录中的 `.XClaw-preinstalled.json`

### 文案策略

为了和 QClaw 截图保持一致，界面上可以显示 `内置技能` 标签；但工程语义必须映射到 `xclaw-preinstalled`。如果证据链拿不到，就不能显示这枚标签。

## 技能说明国际化

技能说明不能一刀切地声称“全部国际化”，因为来源并不统一。

### 当前事实

1. 本地技能卡片的说明主要来自 runtime / provider 返回的 `description`。
2. 其中一部分技能是 `XClaw` 自己预装或高频集成的，我们可以维护稳定的说明词典。
3. `ClawHub / SkillHub / 第三方 runtime` 动态返回的技能说明，不受 `XClaw` 完全控制。

### 正确策略

1. `XClaw` 维护一层本地描述覆盖词典，按 `slug / id` 做键。
2. 如果当前语言存在对应描述，就优先显示本地化说明。
3. 如果不存在覆盖，就回退到技能原始说明。
4. 不对第三方动态说明谎称“已完整国际化”。

### 覆盖范围

优先覆盖：

1. `XClaw` 预装技能
2. 当前界面高频展示、可控接入的技能
3. 后续需要产品化表达的精选技能

这层放在前端 i18n 词典中，优点是：

1. 不污染 gateway / host-api 原始数据
2. 不影响 provider adapter 的原始返回
3. 可逐步扩充，不阻塞整个技能中心重构

## 页面结构

### 顶部头部

保持两行：

1. 标题：`技能管理`
2. 副说明：`为你的智能体提供预封装且可重复的最佳实践与工具`

要求：

1. 不做 hero，不做大面积彩色头图。
2. 留白像桌面应用内容区，不像网页落地页。

### 工具栏

保持 QClaw 的主结构：

1. 左侧：大搜索框
   - 文案：`搜索已经安装的技能`
2. 右侧：`添加技能`

要求：

1. 搜索范围仅限本地技能集合。
2. 不在主工具栏保留当前的多筛选、多批量按钮。
3. `添加技能` 是次级入口，不是当前页的第二主搜索器。

### 主体网格

主列表使用桌面自适应卡片网格：

1. 默认桌面窗口下优先两列，这是主要工作密度。
2. 窄窗口自动退为一列，避免卡片被硬压扁。
3. 超宽窗口最多提升到三列，不做无限扩张的瀑布流或商店墙。
4. 卡片高度控制在稳定区间，避免网页 market 感。

每张卡片包含：

1. 左上：技能图标或 emoji
2. 标题：技能名
3. 描述：最多两行
4. 右上：启用开关
5. 底部左侧：来源标签
6. 底部右侧：更多菜单

### 空状态

必须与 QClaw 目标语义一致：

1. 仍然保留页面头部和搜索框
2. 主体显示轻量空态
3. 空态中提供内联 `添加技能` 入口
4. 不显示管理后台式错误墙或重提示框

## 卡片规则

### 卡片本体

卡片只承担轻操作：

1. 查看基本信息
2. 直接启停
3. 打开详情
4. 打开更多菜单

卡片不直接承担：

1. API key 编辑
2. 环境变量编辑
3. README 大段展示
4. 目录路径面板

### 标签

标签是轻语义，不是状态墙。建议映射：

1. `xclaw-preinstalled` -> `内置技能`
2. `openclaw-managed` -> `已安装`
3. `openclaw-workspace` -> `工作区`
4. `openclaw-extra` -> `额外目录`
5. `agents-personal` / `agents-project` -> `Agent`
6. 其他 -> `其他来源`

### 更多菜单

默认只保留少量动作：

1. 查看详情
2. 打开目录
3. 打开 README
4. 卸载

如果技能不支持对应动作，该项应隐藏或禁用，并展示原因。不要让更多菜单重新长成后台操作清单。

## 二级层：详情弹窗

详情层对齐 QClaw 的轻量详情弹窗，而不是当前的厚侧抽屉。

### 结构

1. 居中的桌面模态层
2. 保持同一张技能图标、标题、描述
3. 显示来源、版本、目录信息
4. 再下沉显示本项目独有的高级能力

### 承载内容

允许下沉：

1. API key
2. 环境变量
3. 打开目录
4. 打开 README
5. 路径复制
6. 卸载

要求：

1. 默认折叠或分区，不要一打开就出现重表单。
2. 弹窗关闭后，焦点必须回到发起卡片。

## 外部 provider 接入设计

### 总原则

主技能中心与外部技能发现分层：

1. 主页面只管本地技能
2. `添加技能` 才进入外部发现
3. provider 结果不与本地技能卡片直接混排

### ClawHub

`ClawHub` 是已有可靠主链路，必须继续复用 Electron main 里的 `ClawHubService`，不能退回纯提示词安装。

正确做法：

1. 在“从 ClawHub 搜索”二级流里搜索
2. 用户选择技能后，生成结构化安装草案
3. 跳转聊天页，由自然语言承接用户感知
4. 但安装实际仍要能落回 `/api/clawhub/install` 这条可靠 host action

### 腾讯 SkillHub

`腾讯 SkillHub` 当前能确认的是：

1. 存在真实搜索 API
2. 存在 agent / human 两类安装语义
3. 内嵌 QClaw 时会向父窗口发 `INSTALL_SKILL`

因此 `XClaw` 不能直接假设它是稳定的桌面安装 API。正确接入方式是：

1. 新建独立 provider adapter
2. 负责搜索、详情字段归一化、安装草案生成
3. 不把外站页面整个内嵌为主交互
4. 安装时仍跳聊天，但聊天拿到的是结构化草案，而不是完全自由发挥的 prompt

### provider 结果标识

只要出现外部 provider 结果，必须使用 provider-qualified id，不能只用 `slug`。例如：

1. `clawhub:pdf`
2. `skillhub:excel-analyzer`

否则后续和本地技能合并时会出现冲突。

## 聊天安装流

用户要求“安装时跳聊天窗口，使用自然语言安装”，这个目标成立，但不能做成纯模型型工作流。

### 正确的聊天安装结构

1. 技能页生成 `install draft`
2. `install draft` 至少包含：
   - provider
   - providerSkillId
   - slug
   - name
   - 推荐安装动作
   - 附加元数据
3. 聊天页接收 draft 后生成自然语言安装意图
4. 实际执行分两类：
   - `ClawHub`：聊天页通过可靠 host action 触发确定性安装
   - `SkillHub / GitHub 导入`：聊天页使用固定草案 prompt 发起，不允许模型自行编造安装命令

### 聊天 handoff 契约

1. 从技能页跳到聊天页时，不自动开始执行。
2. 用户必须明确发送一次草案消息，执行才开始。
3. 在发送前取消，应直接回到技能页并恢复原状态。
4. `ClawHub` 路径在发送后有确定性的成功/失败结果，可驱动技能页刷新。
5. `SkillHub / GitHub 导入` 路径在发送后属于“聊天协作执行”，`XClaw` 只保证草案 prompt 与上下文固定，不伪造自动安装完成事件。
6. 这意味着技能页对这三类路径只承诺：
   - 发送前可取消并完整恢复
   - 发送后可手动返回技能页
   - 返回时恢复原搜索和 provider 结果上下文
   - 不承诺自动判断“安装已完成”

### 连续性要求

从技能页跳聊天时，必须保证：

1. 保留当前技能页搜索词和滚动位置
2. 聊天取消后能返回技能页
3. `ClawHub` 成功/失败后，技能页能感知结果并刷新
4. `SkillHub / GitHub 导入` 返回技能页时恢复原 provider 结果列表与查询上下文

## 交互契约

这一部分是三次 review 都指出的缺口，必须在设计阶段写死。

### 键盘与焦点

1. `Tab`：按头部、搜索框、添加技能、卡片、详情弹窗顺序移动
2. 卡片网格支持方向键移动
3. `Enter / Space`：打开卡片或触发按钮
4. `Esc`：
   - 关闭添加菜单
   - 关闭详情弹窗
   - 关闭 provider 搜索面板
5. 焦点返回到触发源

### 开关状态

启停开关必须有完整状态模型：

1. `idle`
2. `pending`
3. `success`
4. `rollback`
5. `disabled-with-reason`

如果切换失败，卡片要保留状态回滚和错误反馈，不能只闪一下。

### 二级动作访问

1. `...` 菜单不能只依赖 hover
2. 必须支持键盘触发
3. 必须支持触控板/右键路径

## 桌面视觉要求

### 视觉方向

1. 白底、轻边框、低阴影、圆角卡片
2. 低饱和度，不做大面积彩色 banner
3. 开关、标签、更多按钮都做桌面级弱对比
4. 搜索框与按钮像桌面内容区控件，不像网页 marketing 搜索条

### 跨平台约束

必须显式兼容：

1. `macOS`
2. `Windows`
3. `125% / 150% / 200%` 缩放
4. 高对比模式
5. `prefers-reduced-motion`

### 布局约束

1. 设定最小卡片宽度，避免被压成窄条
2. 窗口缩小时允许退到一列，但不允许产生瀑布流错位
3. 长标题、长描述、长本地化文案都必须稳定截断

## 成功标准

当这轮设计落地后，页面应满足：

1. 用户第一眼看到的是“技能中心”，不是“管理后台”。
2. 主工具栏只承担本地搜索和添加技能。
3. 主网格只承载本地技能，不混入外部 provider 结果。
4. `内置技能` 标签只出现在真实 `xclaw-preinstalled` 数据上。
5. `ClawHub / SkillHub` 搜索与安装走次级流，并能回到聊天完成安装。
6. 鼠标、键盘、缩放和跨平台行为都符合桌面应用预期。

## 当前阶段结论

本轮设计经过三次子代理 review 后，已从“把所有东西塞进一页”修正为更严格的双层模型：

1. 主页面全面对齐 QClaw 技能管理中心
2. 外部发现进入 `添加技能` 次级流
3. 来源语义按 `xclaw-preinstalled` 等产品级 provenance 重新校正
4. 安装体验保持“跳聊天 + 自然语言”，但执行链必须挂在可靠 adapter / host action 上

这份文档当前只作为设计基线，尚未进入实现。
