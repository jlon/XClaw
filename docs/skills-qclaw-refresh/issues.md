# 技能中心 QClaw 桌面化对齐问题记录

## 当前已知风险

1. `src/pages/Skills/index.tsx` 目前是单文件重页面，主结构、安装流、详情层、配置表单高度耦合，重构时很容易再次把职责堆回一处。
2. 技能说明现在已经支持“本地词典覆盖 + 原文回退”，但第三方动态技能说明还不是完整翻译体系，后续需要继续补覆盖。
3. 现有 store 的搜索与安装模型是单 provider 的 `ClawHub` 语义，不能直接承载双 provider。
4. 如果把 `ClawHub / SkillHub` 搜索结果直接混入主搜索框，会偏离 QClaw 目标结构。
5. `腾讯 SkillHub` 当前能确认的是前端接口和安装草案形态，不是稳定文档化的桌面 API，必须隔离在 adapter 层。
6. 用户要求“跳聊天窗口，自然语言安装”，但 `ClawHub` 的可靠执行链当前在 Electron main；如果只做 prompt 跳转而不接 host action，会退化成不稳定方案。
7. provider 结果如果继续只用 `slug` 作为主键，会在本地技能和多 provider 合并时产生冲突。
8. 主卡片上如果继续塞太多动作，很容易再次退化成后台操作面板。
9. 当前技能页还没有桌面级键盘/焦点契约，后面如果只改视觉不补交互，会出现“像桌面，行为不像桌面”的半成品。
10. `SkillHub` 的前端接口没有稳定文档，真实参数和返回结构可能继续漂移，后续仍需把 provider 适配层视为易变边界。
11. provider 结果与本机已安装技能的过滤当前以 `slug / id / providerSkillId` 做键匹配；如果后续某个来源切换了命名规则，仍可能出现漏过滤或误过滤，需要持续观察。
12. `SkillHub` 当前并没有公开稳定的“给 Agent 的安装提示词”字段；现阶段 `XClaw` 采用产品侧确定模板来生成聊天草案，而不是依赖第三方接口直接下发 prompt。
13. `SkillHub` 安装草案当前以 `slug` 作为目标技能标识，以保证和 CLI 语义一致；如果未来某些技能的 CLI 安装标识与搜索返回 `slug` 不一致，需要补 adapter 映射。
14. `Skills -> Chat` 这条链已经补了 E2E，但测试夹具必须和 provider adapter 的真实返回保持一致，尤其是 `installCapability`。如果夹具缺这个字段，会制造“点击发送到聊天没有跳转”的假象。

## 后续重点观察

1. `添加技能` 菜单里 QClaw 对齐项与 XClaw 扩展项的层级是否清晰，用户是否会误以为全部来自 QClaw。
2. 主网格在技能名很长、描述很长、emoji 图标很复杂时是否仍稳定。
3. `内置技能` 标签是否只出现在真实 `xclaw-preinstalled` 数据上。
4. `ClawHub` 安装从技能页跳聊天后，是否仍能稳定落回已有 host 安装能力。
5. `SkillHub` provider 如果接口失效，失败路径是否足够体面，不会拖垮技能页主体验。
   - 当前已修正为 `page/pageSize/sortBy/order/keyword -> data.skills`，但仍需关注后续腾讯侧接口变更
6. 从技能页跳聊天安装后，返回技能页时是否保留原查询、滚动位置和选择状态。
7. `Windows` 下缩放到 `125% / 150% / 200%` 时，双列是否仍保持桌面密度。
8. `macOS` 下详情弹窗、菜单、开关、搜索框的 hover/active/focus 是否足够细腻，不显网页。
9. `SkillHub` 的 `chat-prompt` 安装流现在已经固定导航到当前聊天页；后续仍需观察从技能页来回切换时，用户是否会期望“自动发送”而不是“原样带入输入框”。
