# Agent 工作台重构问题清单

## 当前已确认问题

### 1. 旧设计的核心问题不是功能少，而是形态错

上一版把 `Agents` 做成：

- 左侧 source list
- 右侧 detail pane

这能承载 CRUD，但做不出用户要的桌面级质感。  
真实问题有三条：

- 本地 Agent 更像后台资源列表，不像“角色卡”
- 人格文件编辑被压成窄 pane，天然不舒服
- 市场与本地 Agent 混成一个面，发现与编辑互相干扰

### 2. “我的 Agent”和“Agent 市场”没有被明确拆成两种任务

用户当前的真实需求其实是两条完全不同的工作流：

- 维护我已有的 Agent
- 发现并安装新 Agent

如果还继续做成同一个列表 + 同一个 detail pane，只会越来越乱。

### 3. 本地 Agent 识别资产不够

当前 Agent 的可视识别过弱：

- 名称重复时难辨识
- 首字母圆章过于占位符
- 不像真正的“角色卡”

这也是用户反复觉得“后台感重”的原因之一。

### 4. 人格文件编辑区还没有进入正确工作区语义

真实问题不是“编辑器不好看”，而是：

- 角色选择
- 文件切换
- 内容编辑
- 文件操作

四件事还没有形成一个统一的工作区。

### 5. 市场页需要独立布局，不能只是 tab 里的另一种列表

市场不只是“另一个 tab”。  
它是发现、筛选、安装的完整界面，应该拥有：

- 卡片浏览
- 详情预览
- 安装动作

### 6. 页头、浏览区、detail pane 曾经职责混乱

当前已经验证过一个真实问题：

- 页头同时挂模式切换、创建、安装、刷新，会把浏览工具和全局导航混在一起

这会直接破坏桌面工作台的动线。  
现在已经改成：

- 页头只负责标题和模式切换
- 浏览区自己负责搜索/筛选/创建/刷新
- detail pane 只负责当前对象的深入编辑与安装

## 已收敛结论

### 1. Agent 页改成双模式工作台

- `我的 Agents`
- `Agent 市场`

### 2. 本地 Agent 用自适应卡片浏览区，不再用 source list 做主浏览

卡片负责：

- 浏览
- 发现
- 选择

### 3. 右侧 detail pane 继续保留，但职责改变

它不再是“整个页面唯一主角”，而是：

- 选中卡片后的 detail workbench
- 承接概览、人格文件、绑定与运行

### 4. 人格文件仍只开放 `workspace`

这条安全边界不变：

- `workspace` 可写
- `agentDir` 只读事实面

### 5. 市场与本地 Agent 共用卡片语法，但不共用同一信息密度

- 本地卡片偏管理
- 市场卡片偏发现

## 技术与产品边界

### 1. 头像不能依赖在线生成

必须满足：

- 本地 deterministic
- 跨平台稳定
- 可重复生成

### 2. 不能为了“统一创建”硬做 duplicate

`duplicate` contract 还没锁死，继续保持暂缓。

### 3. 市场 v1 仍是内置 catalogue

不做开放社区。

## 未决问题

### 1. 自适应卡片浏览区尚未按设计完全落地

设计红线已经锁死：

- 默认窗口 `1200 x 800` 下优先 `2` 列
- `>=1500px` 三列
- `1200-1499px` 两列
- `980-1199px` 一列且 detail 常驻
- `<980px` 改成覆盖式/切换式承接

当前真正未完成的不是规则，而是实现还没完全落到这些规则上。

### 2. 人格文件编辑区是否需要左右子分栏

当前倾向：

- `文件切换条 + 编辑器` 两段式

不继续拆成三栏。

### 3. 头像方案已收敛，后续只剩是否迁移

当前 v1 事实已经锁定：

- 继续保留现有自研 deterministic 头像
- 主种子使用 `agent.id`
- 不在本轮切 `dicebear`

后续如果确有收益，再评估是否迁移到 `jdenticon`。

## 当前最高优先级

1. 先把 `我的 Agents / Agent 市场 / detail workbench` 的布局骨架落稳
2. 继续把 detail workbench 的层级做稳
3. 最后继续优化 copy、安装动线和细节质感

## 三轮 review 后新增的硬问题

### 1. 浏览区和 detail pane 的职责边界必须锁死

如果实现时又把：

- 标签
- 市场
- 文件编辑
- 删除/重命名

全部塞回右侧 pane，页面会再次退回网页后台。

### 2. “卡片式”很容易走偏成营销卡片

必须避免：

- 大插画
- 过重阴影
- 厚 glow
- 信息堆满卡片

卡片只做识别、摘要和入口，不做完整详情页。

### 3. 头像方案已经锁定为现有自研 deterministic 路线

本轮不再继续讨论：

- 是否切 `dicebear`
- 是否新增头像依赖

后续只评估是否迁移到 `jdenticon`。

### 4. 市场安装后的回跳和高亮行为要先锁 UX

这条如果不先锁，后面很容易出现：

- 安装成功但用户找不到新 Agent
- 卡片已生成但 detail pane 仍停留在市场详情

## 本轮实现后新增观察

### 1. 右侧 detail pane 虽然已经进入工作台语法，但还没有完全摆脱后台感

当前已经从“窄 inspector”推进到 `Hero -> chips -> tabs -> section`，但：

- 概览区的信息卡仍偏工程事实展示
- 人格文件编辑区的工具条仍可继续压平
- 市场详情的来源说明仍偏后台说明文

### 2. 旧 `AgentListPane` 已经不再是主入口

当前主入口已切换到卡片浏览区。后续要决定：

- 保留 `AgentListPane` 作为兼容组件
- 还是在新版稳定后彻底退役

### 3. detail workbench 仍然偏重单文件大组件

虽然右侧结构已经收成 `Hero -> Actions -> Tabs -> Sections`，但实现还集中在 [src/pages/Agents/index.tsx](/Users/jianglong/workspace/XClaw/src/pages/Agents/index.tsx) 一个大组件里。后续如果继续加市场细节或人格文件动作，很容易再次膨胀。

### 4. 创建/安装链路曾经不是原子提交

这条已被真实验证过：

- 智能体先写入 `openclaw.json` 与本地目录
- 再做 provider sync / runtime 应用

只要后置步骤抛错，接口就会返回失败，但前面的配置和目录已经落盘。  
这会直接造成：

- UI 以为创建失败
- 磁盘和配置里其实已经有新智能体
- 重试会生成 `-2 / -3` 重复实体

当前这条问题已经修复，但必须继续作为铁律记住：**后置失败必须回滚**。

### 5. 市场安装曾经依赖运行时外网

之前市场安装直接拉 GitHub raw 模板，这不满足“真实可用”：

- 需要代理时容易失败
- 离线时必然失败
- GitHub 波动会把主链路打断

当前已改成仓库内置模板资产，但这条问题也需要保留为铁律：**安装链路不能把外网当主依赖**。

### 4. 配置保存与 runtime 应用必须拆开

这轮已经验证出一个真实边界：

- 名称修改属于轻配置，不应强制重启 runtime
- 模型覆盖属于运行时相关配置，需要异步应用

所以 `智能体设置` 后续必须继续坚持：

- 保存成功和 runtime 应用成功不是一回事
- UI 只能给局部“正在应用”的反馈
- 不能回退成全局重遮罩，也不能把所有配置一律同步重启

### 4. Linux 手工 smoke 仍缺验收清单

当前文档一直强调 mac / Windows，但项目本身是 cross-platform Electron app。  
如果本轮不做 Linux 手工验收，就必须在测试方案里把 Linux smoke 明确列出来，避免后面默认忽略。

### 5. `绑定与运行` 虽然已经独立，但 overview 事实卡还偏后台

这轮已经把：

- 概览
- 人格文件
- 绑定与运行
- 市场底部安装 action

这几层分开了，但 overview 的事实卡仍偏工程展示，需要继续压掉后台感。

### 6. 页头和浏览工具栏不能重复承担模式说明

如果同时保留：

- 大标题
- 描述文案
- 模式切换
- 浏览工具条

`Agents` 会立刻回到后台信息架构。当前已经收成轻工具条，但后续必须继续守住：模式切换只负责切模式，搜索/筛选/安装入口只留在各自浏览工具条里。

### 7. 本地 Agent 卡片仍缺真实“角色摘要”合同

当前 `AgentSummary` 真实只有：

- `id`
- `name`
- `modelDisplay`
- `channelTypes`
- `workspace / agentDir`

还没有：

- `role`
- `description`
- `updatedAt`

所以本地卡片目前只能做到“角色卡结构”，还不能完全做到“角色卡语义”。后续如果要继续贴近目标，必须先补真实合同，而不是继续拼假文案。

### 8. 市场国际化目前仍然是“可信回退”，不是完整多语内容库

当前市场已经支持国际化，但要把边界说清楚：

- `zh / en / ja` 已覆盖壳层文案、章节标题、安装动作
- 模板 `name / headline / summary / highlights` 支持 locale key 覆盖
- 如果模板没有人工校对过的本地化内容，继续显示上游源语言

这意味着：

- 当前实现是可信的
- 但还不能宣称“58 个模板都已经完整多语化”

如果后续要把市场当成真正的多语商店，需要补内容运营链，而不是继续依赖运行时假翻译。

### 9. 市场 seed 是“真实快照”，不是实时镜像

这轮已经补了同步脚本，也把 seed 升级成了富元数据 catalogue。  
但它仍然是快照：

- 上游仓库更新后，不会自动即时反映到本地市场
- 需要显式运行同步脚本并复核内容质量

所以 v1 的正确定位是：

- 内置受控 catalogue
- 基于上游 `SOUL.md` 的真实内容快照
- 不是实时在线市场

### 10. 少数模板的摘要质量仍需人工校正

虽然这轮已经修掉了 `ux-researcher / video-scripter / research-assistant / study-planner` 这类直接退回 slug 的问题，但仍不能假设 58 个模板都达到了同一写作质量。

真实边界是：

- 生成器已经足够把“空壳目录”升级成“可用市场内容”
- 但如果要达到“商店级文案一致性”，仍需要后续人工抽样校正

### 11. 市场类型合同仍有多处维护点

当前这条链虽然已经可用：

- `electron/shared/agent-market-seed.json`
- `electron/utils/agent-market.ts`
- `src/types/agent-market.ts`
- `src/pages/Agents/index.tsx`

但严格说还没有收成单一事实源。  
electron 侧和 renderer 侧仍在各自维护市场合同，当前只是字段恰好同步。

这不影响本轮交付，但如果后续继续扩字段，存在类型漂移风险。

### 12. 新建智能体此前缺少模型覆盖入口

这轮之前，`编辑智能体` 已经支持 `modelRef`，但 `新建智能体` 弹窗只有名称输入：

- 用户无法在创建时选择具体 provider/model
- `POST /api/agents` 也只接收 `{name}`
- 结果是“创建后再补改模型”，动线割裂

现在这条链已经补齐：

- 新建弹窗支持搜索并选择可用模型
- 保存完整 `modelRef`
- 默认模型继承仍然可选

后续需要继续守住一条边界：

- 显示层可以只露 `modelId`
- 但持久化和路由合同必须继续使用完整 `modelRef`
