# 智能体头像语义化重构问题清单

## 当前已确认问题

### 1. 现有头像没有角色语义

当前头像只保证稳定，不保证“像这个智能体”。

### 2. 市场已有 `avatarSeed` 但没有真正进入渲染链路

这导致数据上看起来有准备，实际 UI 仍然按 `id` 画占位符。

### 3. 本地智能体有 `SOUL.md`，但头像系统没有使用

这说明当前链路浪费了最有价值的角色信息。

### 4. 直接照搬 control-center 会造成风格割裂

它的像素动物和 XClaw 现有工作台语法不属于同一种产品语言。

## 已收敛结论

### 1. 不走远程 DiceBear API

原因：

- 离线能力会变差
- 会引入外部依赖
- 本地智能体信息不应该发到外部服务

### 2. 不复刻 control-center 的像素表现层

原因：

- 风格不对
- 判定逻辑仍然过度依赖 `agentId`

### 3. 采用 DiceBear 本地库 + `bottts-neutral`

这是当前最符合 XClaw 产品气质的路线。

### 4. 语义判定坚持规则引擎，不用 AI

原因：

- KISS
- 可测试
- 离线
- 不会因为提示词或模型变化而漂移

## 未决问题

### 1. 本地语义材料是否只读 `SOUL.md`

当前倾向：

- `SOUL.md` 为主
- `IDENTITY.md` 为辅
- `AGENTS.md` 仅作补充

这条在实现前要锁。

### 2. archetype 数量要不要控制在 9 个以内

当前建议是 9 个左右。  
如果 archetype 过多：

- 关键词词典会膨胀
- 测试会变脆
- 视觉差异难以保持统一

### 3. 是否把 `avatarProfile` 做成 API 合同

当前建议是“做成 API 合同”，因为：

- 本地卡片列表需要首屏直出
- renderer 不适合逐个读文件再判定

### 4. 是否把 DiceBear 渲染放在 renderer

当前倾向：

- profile 在后端或 catalogue 侧生成
- SVG/dataUri 在 renderer 生成

这样可以少传输字符串，也更接近 UI 组件职责。

## 当前最高优先级

1. 先锁共享语义合同
2. 再锁本地智能体富化入口
3. 最后替换 `AgentAvatar` 的表现层

## 当前风险

### 1. 关键词词典如果过度扩张，会违反 KISS

必须克制在少量 archetype 和少量核心关键词，不做假智能。

### 2. 如果直接把完整 `SOUL.md` 暴露到前端，会扩大数据面

这不必要，也不符合最小暴露原则。

### 3. 如果没有旧 identicon fallback，新头像链路失败会直接变成空白

这不能接受，必须保留兜底。
