# 工作室多皮肤切换设计

## 背景

当前 XClaw 的工作室已经集成了一套来自 `Star-Office-UI` 的办公室主场景，但 `Star-Office-UI` 仓库本身并不是“多套独立办公室页面”，而是一套主场景加一套资产替换与收藏机制。  
这意味着如果直接把 `join`、`invite`、桌宠、资产编辑抽屉一起接进 XClaw，会把“换皮”需求做成一套失控的场景编辑系统。

本次设计只解决一个明确目标：

- 在 XClaw 的工作室中预置多套办公室皮肤
- 每次进入工作室时自动随机切换一套
- 在工作室内提供一个轻量手动“换皮”入口

## 目标

- 支持办公室主场景的多皮肤随机切换
- 保持现有工作室主场景逻辑、站位、遮挡和动画体系不变
- 每次进入工作室时自动随机一套皮肤
- 在当前这次进入期间，允许用户手动切到另一套皮肤
- 保证切换失败时自动回退到默认皮肤，不能白屏或半套资源错位
- 版本 1 首发至少提供 3 套可用预置皮肤，避免“随机切换”失去意义

## 非目标

- 不接入 `join.html`、`invite.html`
- 不接入桌宠、最小化窗口等独立壳层行为
- 不接入 `Star-Office-UI` 的资产编辑抽屉、收藏的家、AI 生图、单素材替换流程
- 不支持用户自定义上传皮肤
- 不支持改变房间布局骨架、角色路径点、点击区域或遮挡规则

## 方案对比

### 方案 A：运行时预置皮肤包

- 在 XClaw 内部维护若干套固定皮肤清单
- 每套皮肤本质是一个资产映射组合，而不是一份独立页面
- 进入工作室时由 XClaw 外层决定本次皮肤，再传给 `star-office-runtime`
- runtime 负责加载对应资产并刷新场景

优点：

- 复用现有 `star-office-runtime` 与资产刷新链路
- 复杂度最低，最符合当前真实代码结构
- 维护成本可控，不会复制多份 runtime

缺点：

- 前期需要我们自己整理和固化几套皮肤包

### 方案 B：在前端页面中写死多套场景分支

- 在 `electron-standalone.html` 中直接写多套场景逻辑分支
- 切皮时切换不同的前端渲染分支

优点：

- 短期改动看起来直接

缺点：

- 会快速把页面脚本继续写肿
- 违反 `KISS/DRY`
- 后面新增皮肤时需要持续改场景逻辑

### 方案 C：每套皮肤复制一份独立 runtime

- 每套皮肤拥有独立目录、独立页面或独立 runtime
- 切皮时切换不同 runtime

优点：

- 逻辑隔离表面上最强

缺点：

- 资源冗余和维护成本最高
- 与现有工作室集成成本最高
- 容易把“换皮”做成“多套工作室系统并存”

## 结论

采用方案 A。  
原因是它最贴近 `Star-Office-UI` 当前真实能力边界，也最符合 XClaw 已有的工作室集成方式。

## 用户体验设计

### 进入工作室时的随机策略

- 工作室维护一个“本次进入实例”的皮肤锁，不做长期持久化记忆
- 每次从非工作室路由进入工作室时，如果当前实例还没有皮肤锁，则从预置皮肤池中随机选择一套
- 如果皮肤池数量大于 1，默认避开“上一次离开工作室时生效的皮肤”，降低连续两次视觉无变化的概率
- 用户离开工作室后，本次实例的皮肤锁失效；下次重新进入时重新随机
- “上一次进入工作室使用过的皮肤”只在当前 XClaw 应用会话内保留，应用重启后不继承

### 皮肤状态更新规则

- 首次进入工作室并成功应用皮肤后，当前实例皮肤锁更新为该皮肤
- 手动点击“换皮”并成功应用后，当前实例皮肤锁立即更新为新皮肤
- 离开工作室时，将“当前实例皮肤锁”写入“上一次离开工作室时生效的皮肤”
- 下一次重新进入工作室时，只使用“上一次离开工作室时生效的皮肤”作为随机避让参考
- 如果任一次皮肤应用失败且 runtime 已回退到默认皮肤，则当前实例皮肤锁必须更新为默认回退皮肤

### 工作室内的手动换皮

- 在工作室右上角现有 chrome 区放置一个轻量“换皮”入口
- 入口不进入像素场景内部，不污染主画面
- 点击后不打开复杂面板，只执行一次“从除当前皮肤外的可用池中重新随机一套”
- 手动换皮只影响当前这次进入期间的皮肤锁
- 用户本次换到的皮肤会保持到离开工作室为止
- 如果当前只有 1 套可用皮肤，手动“换皮”入口直接隐藏

## 皮肤模型设计

### 基本原则

- 皮肤不是页面
- 皮肤不是布局
- 皮肤不是运行时编辑能力
- 皮肤是一组固定的场景资产映射

### 一套皮肤至少应覆盖的资产

- `office_bg_small`
- 场景中的关键大件贴图或 spritesheet
- 与整体视觉强相关的装饰元素，如海报、植物、沙发、服务器区、猫、办公桌等
- 必要时覆盖主角色和访客使用的视觉资源，但不能改变角色行为逻辑

### 皮肤约束

- 所有皮肤必须沿用同一套房间透视、站位和遮挡骨架
- 不允许修改路径点、交互区域、对象层级规则
- 资源缺失时必须整体回退，不能出现半套资源混搭

## 集成边界

### XClaw 负责

- 判断“是否是一次新的工作室进入”
- 为本次进入实例选择皮肤 key
- 保留上一轮进入使用的皮肤 key 以便随机时避让
- 响应右上角“换皮”按钮并发起一次新的皮肤切换动作

### `star-office-runtime` 负责

- 按皮肤 key 解析对应的资产清单
- 将皮肤资源应用到当前工作室场景
- 在运行中完成一次安全刷新
- 在皮肤应用失败时回退到默认皮肤

### 明确排除的能力

- 不把 `Star-Office-UI` 的资产编辑抽屉搬进 XClaw
- 不让 XClaw 直接操作底层单个 asset 文件
- 不暴露收藏、生成、上传、替换等编辑型动作

## 技术设计

### 数据结构

建议新增一份“皮肤注册表”数据文件，包含：

- 皮肤 key
- 展示名
- 皮肤资源映射
- 是否启用
- 是否为默认回退皮肤

建议每套皮肤是一个稳定的数据对象，而不是在前端代码中写一串条件分支。

建议为版本 1 明确约束：

- 首发仅维护一份内置皮肤注册表
- 注册表中的可用皮肤数不少于 3
- 每套皮肤都必须有完整的默认回退路径
- 只有 `enabled = true` 的皮肤可以进入自动随机池和手动换皮候选池
- 默认回退皮肤默认不进入随机池，除非显式同时标记为可选皮肤

### 状态确认契约

- XClaw 不能在发出换皮命令后立即乐观更新当前皮肤状态
- 只有在 `star-office-runtime` 明确返回“应用成功”确认后，XClaw 才能更新当前实例皮肤锁
- 如果 runtime 返回 `ok = false` 且 `fallbackApplied = true`，XClaw 必须将当前实例皮肤锁更新为默认回退皮肤
- 如果 runtime 返回 `ok = false` 且 `fallbackApplied = false`，XClaw 必须将其视为严重异常并主动切回默认回退皮肤
- “上一次离开工作室时生效的皮肤”只在离开工作室时根据最终确认状态写入
- 手动换皮和首次进入应用皮肤都遵循同一套确认规则

建议将 runtime 返回统一为明确结果对象，至少包含：

- `ok`
- `appliedSkinKey`
- `fallbackApplied`
- `reason`

### 运行链路

1. 用户进入工作室
2. XClaw 判断这是一次新的工作室进入
3. XClaw 根据随机规则选出本次皮肤 key
4. XClaw 在工作室首次加载时通过明确的运行时参数将皮肤 key 传给 `star-office-runtime`
5. runtime 解析皮肤清单并加载对应资源
6. runtime 返回本次应用结果
7. XClaw 仅在收到成功确认后更新当前实例皮肤锁
8. 工作室场景刷新完成
9. 如果用户点击“换皮”，XClaw 重新从除当前皮肤外的可用池中随机一套
10. XClaw 通过单独的运行时切换命令通知 `star-office-runtime` 应用新皮肤
11. runtime 在不重启工作室 surface 的前提下完成刷新并返回结果
12. XClaw 根据确认结果更新当前实例皮肤锁或标记默认回退皮肤已生效

### 失败回退

- 皮肤 key 不存在：回退默认皮肤
- 资源文件缺失：回退默认皮肤
- 资源刷新失败：必须整体回退默认皮肤，不允许保留半套旧资源或半套新资源
- 任一失败场景都必须保证工作室继续可渲染，且最终稳定落在默认皮肤

## 性能要求

- 进入工作室时的随机选皮不能额外引入一次完整 runtime 重启
- 手动换皮应复用现有资产刷新机制，不重新创建工作室 surface
- 皮肤切换过程中允许出现短暂 loading mask，但不能明显卡住整个 XClaw 壳层

## 可观测性

建议记录以下调试信息：

- 本次进入的皮肤 key
- 随机选择来源
- 是否命中过“避开上一次皮肤”
- 皮肤应用耗时
- 是否触发回退以及回退原因

## 风险

- `Star-Office-UI` 当前并没有现成整理好的多套完整皮肤，需要我们自行挑选和固化资产组合
- 如果某套皮肤改动了透视或对象尺寸，角色站位与遮挡会错
- 如果把皮肤设计成前端条件分支，后续会快速失控

## 版本 1 交付边界

版本 1 只交付：

- 若干套预置办公室皮肤
- 进入工作室自动随机
- 右上角轻量手动换皮
- 失败回退与基础日志

版本 1 不交付：

- 皮肤管理面板
- 用户自定义皮肤
- AI 生成皮肤
- 工作室布局变体
- `join / invite / 桌宠` 集成

## 后续可扩展方向

- 皮肤预览缩略图
- 记住用户上次手动切到的皮肤
- 收藏喜欢的皮肤
- 更完整的工作室编辑系统

这些能力都必须作为下一阶段单独特性处理，不能混入本次多皮肤切换实现。
