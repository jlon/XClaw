# 工作室多皮肤切换问题清单

## 当前已确认问题

- `Star-Office-UI` 并没有现成打包好的多套完整办公室皮肤，现有能力更接近“一套主场景 + 资产替换机制”
- 如果把 `join / invite / 桌宠` 一起纳入，会把“换皮”需求扩大成多页面与多窗口集成
- 如果皮肤允许修改布局骨架，会直接破坏角色路径、遮挡和点击区域
- Electron main 侧不能直接复用 `@electron/*` 这类 alias，运行态验证时已经暴露过一次主进程构建失败，后续新增 main 代码必须优先用真实可构建路径
- runtime apply 会改写当前生效的 canonical 前端资产，验证完后必须重新 vendor，避免把运行态试切换留下的产物误当源码提交

## 已接受的版本 1 约束

- 首发皮肤包只替换 `office_bg_small.webp`、`desk-v3.webp`、`sofa-idle-v3.png` 这三类静态大件
- 暂不把 `star-idle`、`star-working`、`plants`、`posters` 等精灵表纳入首发换皮范围
- 首发三套皮肤资源是基于当前主场景素材做程序化调色生成，不是假装来源于 `Star-Office-UI` 现成多套美术包

## 实现阶段重点风险

- 皮肤切换时的刷新成本是否会影响工作室切换流畅度
- 资源缺失时的回退链路是否足够稳
- 右上角“换皮”入口是否会与现有工作室 chrome 冲突
- 如果用 runtime 重启实现换皮，工作室切换和手动换皮都会明显掉帧
- 如果后续要把精灵表也纳入皮肤切换，现有基于 `setTexture` 的静态刷新方案需要升级，不能直接按当前图片替换逻辑硬套
