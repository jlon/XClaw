# 全局主题重构问题跟踪

## 当前已知问题

### 1. 现有主题 token 语义不完整

当前 `globals.css` 只有基础的通用 token，缺少桌面应用真正需要的 `surface / chrome / hover / raised / subtle-border / glow` 语义层。

本轮处理：

- 先补设计约束
- 后续以共享 token 重构为第一优先级

### 2. 当前浅色主题偏“暖米色网页感”

问题不只是暖色本身，而是暖色背景和默认蓝主色放在一起，品牌和界面语义冲突。

本轮处理：

- 主品牌色切到深红铜
- 背景和面板改按石墨体系重建

### 3. 当前深色主题偏通用管理后台

虽然比浅色更稳定，但仍缺少桌面应用的材质层级和品牌识别，视觉上更像普通 dark dashboard。

本轮处理：

- 增加桌面主题扩展 token
- 通过边框、阴影、面板基底和轻 glow 收敛品牌感

### 4. mac / Windows 的差异边界容易失控

如果没有边界，很容易演变成两套主题；如果完全不做适配，又会继续偏网页。

本轮处理：

- 只允许轻度平台 overlay
- 差异仅限材质、边框强度、滚动条、局部应用外壳感受

### 5. 科技感容易滑向 AI 风

如果主色、渐变、阴影和动效失控，很容易做成蓝紫、霓虹、玻璃拟态泛滥的 AI 产品视觉。

本轮处理：

- 禁止蓝紫主色
- 禁止高饱和大面积渐变
- 科技感只来自微光、精细层级和动效节奏

### 6. 品牌色预算如果不写死，后续实现会失控

当前方向已经选定“深红铜”，但如果没有明确使用预算，页面实现阶段很容易出现主按钮、选中态、状态条、卡片高光全部一起上色，最后变成“高饱和铜红后台”。

本轮处理：

- 将品牌色使用预算写入设计稿
- 要求单页品牌高显色面积控制在主区 `10%` 以内

### 7. 只改页面，不改共享控件，会继续回到 web 风

如果第一波只改 `MainLayout / Sidebar / Chat / Channels`，但 `Button / Input / Select` 继续沿用默认 shadcn 表现，整体仍然会保留强烈网页感。

本轮处理：

- 将共享 primitive 纳入第一波
- 强制要求共享控件优先吃新的 token 语义

### 8. 动效和高对比边界还不够硬

当前设计稿里已经提到“克制动效”，但还没有把 `prefers-reduced-motion`、Windows 高对比可用性这类底线写死。

本轮处理：

- 将动效红线和高对比要求升级为正式约束

## 未闭环项

### 1. TitleBar 是否需要更明显的平台差异

当前仅确认“轻度适配”，具体差异力度仍需在示意稿和真实开发态里继续观察。

### 2. 品牌插画和首页卡片是否要同步重画

如果只改颜色而不改首页内容资产，可能仍会保留一部分“旧主题残影”。

### 3. 品牌色 `10%` 预算是否还要再压

如果后面试点页面仍然显得偏热，需要考虑把品牌高显色预算进一步压缩到 `6%-8%`。

### 4. Win/mac 真机桌面观感仍需手工确认

当前代码、页面级回归和构建都已通过，但桌面主题最终是否“像真正的桌面应用”，仍需要真实窗口环境下确认。自动化还不能替代这一层感知验证。

### 5. `Chat` 消息平面虽然已进入新主题体系，但正文排版和欢迎态资产仍需继续观察

当前 `Chat` 已经收掉了旧网页式消息底板，进入统一工作台层级；但消息正文密度、代码块可读性和欢迎态资产热度是否完全达到桌面级产品质感，仍需要在真实窗口里继续判断。

### 6. `Chat` 头部已收掉重复信息，但元信息预算仍需持续控制

当前聊天头部已经从双重标题和重复对象说明收口成单一主标题结构；后续如果继续往头部塞 badge、统计或状态，仍然有重新变乱的风险，必须守住“一主标题、一行元信息、一组工具动作”的预算。

### 7. `Chat` 空态欢迎区也容易重新变成“品牌展示头”

聊天页的问题不只在会话头。空态 welcome 如果继续叠 logo、工作区 badge、状态 pill 和图标卡片，同样会把首屏做成展示页而不是工作台。

本轮处理：

- 空态不再重复渲染会话头
- 欢迎区顶部改成纯文字主焦点
- logo 块、工作区 badge、常驻状态 pill 和顶部图标卡片已移除

### 8. `Chat` 顶部留白如果同时来自全局壳层和页面自身，会继续显得又厚又空

之前聊天页顶部不是单一组件问题，而是 `TitleBar / main padding / Chat header shell` 三层叠加，导致标题虽然已经简化，顶部仍然像保留了一整条空走廊。

本轮处理：

- 聊天路由主工作区不再额外保留上下 padding
- 聊天页自身不再依赖负 margin 抵消全局留白
- 头部背景和上下分割线继续弱化，收成贴顶的轻标题区

### 9. 只要 `TitleBar` 和聊天页都各自承载一份顶部信息，`Chat` 就会持续显得重

页面级 header 再怎么缩，只要顶层仍有独立 `TitleBar`，视觉上就还是双层。桌面聊天页更合理的结构是：顶部只保留一层，信息和动作直接并入最顶栏。

本轮处理：

- 会话标题、元信息和聊天动作已并入 `TitleBar`
- 聊天页内部第二条页头已移除

### 10. 即使收成单层，如果顶栏里仍然常驻标题和会话说明，首屏依然会显得重

聊天场景的第一优先级是消息本身，不是会话说明。顶部即使只剩一层，只要还长期展示标题和元信息，就仍然会压缩首屏内容。

本轮处理：

- 顶栏中的聊天标题和会话元信息已继续移除
- 聊天 route 顶部只保留必要动作

### 11. `gateway 已连接 | port ...` 这类底部状态条会把聊天页做成监控面板

对正常聊天而言，`port / pid` 没有用户价值；把基础设施细节常驻暴露在输入区下方，只会持续占用注意力。

本轮处理：

- 聊天页底部整条 gateway 状态栏已移除
- gateway 微状态已继续上移到顶栏工具区，避免占用输入区主任务空间
- 过渡态和异常态改由 placeholder / tooltip 轻量表达
- 顶栏微状态已补低振幅呼吸，避免静态点在真实桌面窗口里过于无感

## v1 接受的取舍

- 先统一视觉系统，再逐页做完整重绘
- 先不做完整插画系统升级
- 先不处理所有历史页面里的零散品牌色残留

## 后续观察项

- 深色模式下铜红发光是否需要进一步压低
- Windows 下高对比设置是否需要单独兜底
- 首页插画和功能卡片是否需要重新设计以匹配新主题
- 共享 `Button / Input / Select` 改造后是否会暴露更多历史页面的脏样式
- 第二波页面虽然已去掉固定暖色和默认蓝，但仍需手工确认图表、状态色与品牌色的热度是否平衡
- `Setup` 的代码和自动化验证已经闭环，但 Win/mac 真机感知验证仍未完成
