# 全局主题重构问题跟踪

## 当前已知问题

### 1. 现有主题 token 语义不完整

当前 `globals.css` 只有基础的通用 token，缺少桌面应用真正需要的 `surface / chrome / hover / raised / subtle-border / glow` 语义层。

本轮处理：

- 先补设计约束
- 后续以共享 token 重构为第一优先级

### 2. 当前浅色主题偏“暖米色网页感”

问题不只是暖色本身，而是暖色背景和默认蓝主色放在一起，品牌和界面语义冲突。

本轮处理：

- 主品牌色切到深红铜
- 背景和面板改按石墨体系重建

### 3. 当前深色主题偏通用管理后台

虽然比浅色更稳定，但仍缺少桌面应用的材质层级和品牌识别，视觉上更像普通 dark dashboard。

本轮处理：

- 增加桌面主题扩展 token
- 通过边框、阴影、面板基底和轻 glow 收敛品牌感

### 4. mac / Windows 的差异边界容易失控

如果没有边界，很容易演变成两套主题；如果完全不做适配，又会继续偏网页。

本轮处理：

- 只允许轻度平台 overlay
- 差异仅限材质、边框强度、滚动条、局部应用外壳感受

### 5. 科技感容易滑向 AI 风

如果主色、渐变、阴影和动效失控，很容易做成蓝紫、霓虹、玻璃拟态泛滥的 AI 产品视觉。

本轮处理：

- 禁止蓝紫主色
- 禁止高饱和大面积渐变
- 科技感只来自微光、精细层级和动效节奏

### 6. 品牌色预算如果不写死，后续实现会失控

当前方向已经选定“深红铜”，但如果没有明确使用预算，页面实现阶段很容易出现主按钮、选中态、状态条、卡片高光全部一起上色，最后变成“高饱和铜红后台”。

本轮处理：

- 将品牌色使用预算写入设计稿
- 要求单页品牌高显色面积控制在主区 `10%` 以内

### 7. 只改页面，不改共享控件，会继续回到 web 风

如果第一波只改 `MainLayout / Sidebar / Chat / Channels`，但 `Button / Input / Select` 继续沿用默认 shadcn 表现，整体仍然会保留强烈网页感。

本轮处理：

- 将共享 primitive 纳入第一波
- 强制要求共享控件优先吃新的 token 语义

### 8. 动效和高对比边界还不够硬

当前设计稿里已经提到“克制动效”，但还没有把 `prefers-reduced-motion`、Windows 高对比可用性这类底线写死。

本轮处理：

- 将动效红线和高对比要求升级为正式约束

## 未闭环项

### 1. TitleBar 是否需要更明显的平台差异

当前仅确认“轻度适配”，具体差异力度仍需在示意稿和真实开发态里继续观察。

### 2. 品牌插画和首页卡片是否要同步重画

如果只改颜色而不改首页内容资产，可能仍会保留一部分“旧主题残影”。

### 3. 品牌色 `10%` 预算是否还要再压

如果后面试点页面仍然显得偏热，需要考虑把品牌高显色预算进一步压缩到 `6%-8%`。

### 4. Win/mac 真机桌面观感仍需手工确认

当前代码、页面级回归和构建都已通过，但桌面主题最终是否“像真正的桌面应用”，仍需要真实窗口环境下确认。自动化还不能替代这一层感知验证。

### 5. `Chat` 消息平面虽然已进入新主题体系，但正文排版和欢迎态资产仍需继续观察

当前 `Chat` 已经收掉了旧网页式消息底板，进入统一工作台层级；但消息正文密度、代码块可读性和欢迎态资产热度是否完全达到桌面级产品质感，仍需要在真实窗口里继续判断。

### 6. `Chat` 头部已收掉重复信息，但元信息预算仍需持续控制

当前聊天头部已经从双重标题和重复对象说明收口成单一主标题结构；后续如果继续往头部塞 badge、统计或状态，仍然有重新变乱的风险，必须守住“一主标题、一行元信息、一组工具动作”的预算。

### 7. `Chat` 空态欢迎区也容易重新变成“品牌展示头”

聊天页的问题不只在会话头。空态 welcome 如果继续叠 logo、工作区 badge、状态 pill 和图标卡片，同样会把首屏做成展示页而不是工作台。

本轮处理：

- 空态不再重复渲染会话头
- 欢迎区顶部改成纯文字主焦点
- logo 块、工作区 badge、常驻状态 pill 和顶部图标卡片已移除

### 8. `Chat` 顶部留白如果同时来自全局壳层和页面自身，会继续显得又厚又空

之前聊天页顶部不是单一组件问题，而是 `TitleBar / main padding / Chat header shell` 三层叠加，导致标题虽然已经简化，顶部仍然像保留了一整条空走廊。

本轮处理：

- 聊天路由主工作区不再额外保留上下 padding
- 聊天页自身不再依赖负 margin 抵消全局留白
- 头部背景和上下分割线继续弱化，收成贴顶的轻标题区

### 9. 只要 `TitleBar` 和聊天页都各自承载一份顶部信息，`Chat` 就会持续显得重

页面级 header 再怎么缩，只要顶层仍有独立 `TitleBar`，视觉上就还是双层。桌面聊天页更合理的结构是：顶部只保留一层，信息和动作直接并入最顶栏。

本轮处理：

- 会话标题、元信息和聊天动作已并入 `TitleBar`
- 聊天页内部第二条页头已移除

### 10. 即使收成单层，如果顶栏里仍然常驻标题和会话说明，首屏依然会显得重

聊天场景的第一优先级是消息本身，不是会话说明。顶部即使只剩一层，只要还长期展示标题和元信息，就仍然会压缩首屏内容。

本轮处理：

- 顶栏中的聊天标题和会话元信息已继续移除
- 聊天 route 顶部只保留必要动作

### 11. `gateway 已连接 | port ...` 这类底部状态条会把聊天页做成监控面板

对正常聊天而言，`port / pid` 没有用户价值；把基础设施细节常驻暴露在输入区下方，只会持续占用注意力。

本轮处理：

- 聊天页底部整条 gateway 状态栏已移除
- gateway 微状态已继续上移到顶栏工具区，避免占用输入区主任务空间
- 过渡态和异常态改由 placeholder / tooltip 轻量表达
- 顶栏微状态已补低振幅呼吸，避免静态点在真实桌面窗口里过于无感

### 12. `Chat` 工作区如果没有统一宽度基线，消息区、错误条和输入坞站会继续各自漂移

之前聊天页的欢迎态、消息工作台、错误条和输入区分别使用了不同的 `max-width` 与节奏规则，所以底部输入区即使单独修宽度，也只是局部补丁。

本轮处理：

- 新增共享 `app-chat-workbench` 基线
- 欢迎态、消息工作台、错误条和输入坞站改为共用这一条宽度约束
- 输入坞站、按钮和 textarea 的纵向尺寸一起上调，避免只靠 padding 伪装“更高”

### 13. 如果聊天输入区继续沿用一条横向控制带，左右两端会始终显得臃肿

之前的聊天输入区把附件、`@`、模型、发送都塞在一条横向主轴上，所以无论怎么调高度，左右两端都会继续鼓成两块，与参考图里“写作区在上、工具行在下”的工作台结构不一致。

本轮处理：

- 输入区改成上层写作区、下层工具行
- 附件 / `@` / 模型切到底部左侧轻工具组
- 发送按钮独立落到右下角
- 模型选择从长胶囊改成小图标触发器，当前模型信息退到 tooltip / 弹层

### 14. 如果底部工具区仍然作为独立 footer 行存在，输入区会继续出现割裂背景和空洞留白

即使已经改成“两层结构”，只要底部工具仍参与正常文档流，它就会继续拉出一整行高度和宽度，造成工具区像第二层卡片，文字区和工具区之间也会出现视觉割裂。

本轮处理：

- 底部工具区改成同一面板里的覆盖式工具层
- 编辑区增加内边距，为底部工具预留空间
- 左侧图标间距压缩，避免继续形成左下角大块留白

### 15. 如果输入区左下角的三个入口不使用同一套按钮语义，视觉上会天然“错位”

附件和 `@` 如果是轻工具按钮，而模型入口还是带边界、带表单感的独立控件，即使尺寸接近，也会因为轮廓、背景、阴影和留白不同，看起来不在同一条水平线上。

本轮处理：

- 附件 / `@` / 模型入口全部统一为同一套 `app-chat-composer-tool-button`
- 只在弹层打开时给当前入口轻量高亮，不再长期保留独立边界
- 左下角工具组间距继续压缩，对齐 `youclaw` 那种单轨工具节奏

### 16. 如果继续沿用“加高 30%”这类局部放大思路，输入区会越来越像网页卡片而不是桌面工作坞站

本机解包后的 `QClaw.app` 明确显示：它的输入坞站高度并不夸张，`office` 模式外层最小高度约 `71px`，textarea 本体也只有更克制的可编辑高度。之前那种继续整体放大输入区的做法，与真实参考相反。

本轮处理：

- 将 textarea 最小高度从更夸张的 `112 / 88` 收回到 `88 / 72`
- 将发送按钮同步压回更紧凑的 `36px` 级别
- 将编辑区水平内边距补齐，让输入内容更像真正的内嵌编辑区，而不是漂在大白板左上角

### 17. 如果消息工作区继续保留大面积玻璃卡片和强 glow，它再怎么改输入区也还是 AI 味太重

`QClaw` 真正有效的地方不是像素风，而是它的消息区几乎不再被“中央大面板”包起来；助手内容更像自然文档流，用户内容也只是轻量强调。XClaw 当前最重的 AI 味，其实主要来自消息区外层的大卡片、玻璃材质和强阴影。

本轮处理：

- 将消息工作台 `app-chat-thread-stage` 降回透明平面
- 将助手消息气泡降成几乎无边界的文档流
- 将用户气泡保留为品牌强调，但去掉过重 glow 与深阴影

### 18. 如果用户气泡仍然依赖渐变品牌块，它会继续把“发消息”做成 AI 产品式高亮动作

`QClaw` 的发送方气泡并不重，它只是非常淡的暖色 tint，用来区分“这是我发的”，而不是制造强品牌存在感。XClaw 之前的用户气泡即使已经降噪，仍带着偏品牌块的渐变语气。

本轮处理：

- 将发送方气泡背景改成单层淡铜红 tint
- 继续压低边框强度

### 19. 请求级错误如果继续使用整页横向红色横幅，会错误放大故障等级

`LLM request timed out` 这类问题通常只代表当前一次发送失败，不代表整个聊天页或运行时已经不可用。继续把它放在消息区上方做成全宽红条，会持续打断阅读，也会把聊天页做成监控面板。

本轮处理：

- 顶部全宽错误横幅已移除
- 错误提示改成贴近输入区的轻错误气泡
- 只保留真实可执行的关闭动作，不添加没有事实依据的假重试入口
- 进一步去掉大警示 icon，把错误语气压回更接近桌面工作区状态提示的微点胶囊

### 19. 如果助手消息下方继续挂整条 hover 胶囊、厚代码块和“图片下方操作栏”，聊天区仍然会像网页组件集合

`QClaw` 真正成熟的地方不在于像素风，而在于次级交互几乎都收成了文档工作区：复制、时间、代码、预览都只是轻量辅助，不会抢走正文的主导权。XClaw 之前这些部分虽然已经降噪，但仍保留了典型网页组件语气。

本轮处理：

- 助手消息下的复制栏改成无底板的轻元信息行，只保留时间和复制动作
- 代码块改成更平、更克制的文档式代码片段，不再使用厚渐变块
- 图片缩略图和灯箱动作改成更轻的桌面预览表达，移除下方独立操作行

### 20. 如果空态动作、thinking/tool 和运行状态仍然保留按钮卡片语气，聊天页会继续像 AI 面板

正文不是唯一会泄露“AI 味”的地方。空态建议、工具处理中、思考块和运行状态如果都还是圆角胶囊、渐变块、带箭头的动作卡片，用户仍会把这页感知成“AI SaaS 面板”，而不是桌面工作区。

本轮处理：

- 欢迎动作去掉箭头和厚边框，改成更轻的文本动作行
- thinking/tool 的切换头改成更轻的次级行，不再像可点击卡片
- tool status 改成更轻的细分隔状态轨，减少监控面板语气

### 21. 如果常用聊天动作只能靠记忆或反复滚动完成，工作区即使变平也仍然不够“顺手”

桌面级聊天页不只要“看起来克制”，还要让高频动作足够近手。当前模型信息如果藏在弹层里、复制只能靠 hover 猜、上翻历史后还要自己猛滚到底，这些都会让工作流断掉，属于典型的人机细节缺口。

本轮处理：

- 模型图标 hover 直接说明当前使用的模型，避免图标语义过于抽象
- 模型列表把当前选中的模型置顶，减少重复搜索成本
- 用户与助手消息都补上轻量复制入口，但保持低对比，不重新做成操作面板
- 上翻历史时只在需要时显示“快速回到底部”按钮，并用弱提示点表达有新内容积压

### 22. 如果把“运行中小气泡”和“工具状态轨”混用同一套样式，聊天首屏会直接出现残缺视觉

前一轮为了把 tool status 收成更轻的文档轨道，把它改成了“只有左侧细分隔”的状态轨。这套样式用在工具状态上成立，但不能复用到 typing / activity 这类独立提示气泡，否则会看起来像左侧被切掉半边。

本轮处理：

- `tool status` 继续保持轻状态轨
- typing / activity 独立拆成 `runtime pill`
- 两者职责分离，避免后续再互相误伤
- 保留我方品牌色关系，但不再用渐变和 glow 强调“这是用户消息”

### 19. 如果欢迎态继续是“大标题 + 功能卡片”，聊天页首屏仍会像 AI landing，而不是桌面应用启动区

`QClaw` 的 welcome 并不靠大 marketing 卡片成立，它更像一个应用内部的启动区：信息更克制，动作更轻，重点是快速进入工作流。XClaw 之前的欢迎态虽然已经去掉了部分厚表层，但整体仍偏 landing page 语法。

本轮处理：

- 欢迎态改成更轻的启动列表，不再是三张强调型卡片
- 标题尺寸继续下调，文本从居中 marketing 语言收回到更像应用工作区的节奏
- `thinking / tool` 与发送中状态一起降成次级信息轨，不再维持块状提示卡

### 20. 如果欢迎动作和附件继续带明显卡片资产感，聊天页即使主区变平，首屏仍会残留 AI 产品味

`QClaw` 的动作入口和消息附件都不重。它们更多像工作区里的轻行项目和附件缩略，而不是独立展示资产。XClaw 当前这两块虽然已比之前好，但仍偏“模块卡片”。

本轮处理：

- 欢迎动作继续压成轻列表行，只保留最弱边界和 hover 反馈
- 文件附件缩成更紧凑的轻附件条
- 图片缩略不再挂额外卡片表层，回到图片本身承担主要视觉

### 21. 如果为了压缩工具轨而把容器设成 `overflow: hidden`，`@` 和模型弹层会被直接裁掉

这是本轮真实回归，不是视觉问题。`@` 选择器和模型选择器都挂在 `.app-chat-composer-tools` 内部，并且都通过 `bottom-full` 向上弹出；一旦这个工具轨容器变成 `overflow: hidden`，两个弹层会一起“看起来没打开”。

本轮处理：

- 将 `.app-chat-composer-tools` 恢复为 `overflow: visible`
- 保留单行工具轨和紧凑间距，不再通过裁切来维持布局
- 补定向约束，避免后续再把弹层裁掉

## v1 接受的取舍

- 先统一视觉系统，再逐页做完整重绘
- 先不做完整插画系统升级
- 先不处理所有历史页面里的零散品牌色残留

## 后续观察项

- 深色模式下铜红发光是否需要进一步压低
- Windows 下高对比设置是否需要单独兜底
- 首页插画和功能卡片是否需要重新设计以匹配新主题
- 共享 `Button / Input / Select` 改造后是否会暴露更多历史页面的脏样式
- 第二波页面虽然已去掉固定暖色和默认蓝，但仍需手工确认图表、状态色与品牌色的热度是否平衡
- `Setup` 的代码和自动化验证已经闭环，但 Win/mac 真机感知验证仍未完成
