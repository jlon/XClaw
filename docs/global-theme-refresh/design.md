# 全局主题重构设计

## 背景

当前 XClaw 的视觉系统还停留在“通用 web 控件 + 暖色浅背景 + 默认蓝主色”的混合状态，主要问题不是某一个页面不好看，而是全局缺少一套真正的桌面应用主题语言：

- 浅色主题偏暖米色，但主色仍是通用蓝，品牌识别和界面语义不一致
- 卡片、面板、标题栏、侧栏、输入区的层级更像 SaaS 页面，不像桌面生产力应用
- 科技感主要靠零散高亮和页面插画，不是靠系统性的色板、材质、阴影和节奏建立
- mac / Windows 上都能用，但都不够“像它们自己”，桌面感不强

本轮目标不是先调几组颜色，而是先定义一套可落地的全局主题系统，再按系统推进代码重构。

## 目标

- 建立统一品牌主题：`深红铜 + 石墨黑`
- 建立与深色主题成对的浅色主题：`瓷白灰 + 深红铜`
- 保留科技感，但避免蓝紫 AI 产品味和 SaaS 仪表盘感
- 保持一套品牌主题，同时对 mac / Windows 做轻度平台适配
- 将主题能力沉淀为全局 token、共享 surface 规则和状态语义，而不是页面级 hardcode
- 为后续 `Chat / Channels / Agents / Settings / Dashboard` 的统一视觉收敛提供唯一设计基准

## 非目标

- 不做两套完全不同的 mac / Windows 主题
- 不追求完全拟真原生外观复制
- 不在 v1 就把每一个页面都重新设计一遍
- 不引入高饱和霓虹、赛博朋克、蓝紫渐变等容易过时的 AI 风格

## 方向摘要

- 品牌主色不走默认蓝紫 AI 风，改用更克制的深红铜
- 深色背景与面板使用石墨黑和深灰层级，强调桌面应用的稳定感
- 浅色背景与面板使用瓷白灰和冷白灰层级，避免暖米色网页感
- 科技感主要来自光感、层级、材质和局部高亮，不靠大面积高饱和颜色
- 平台适配只做轻度差异：mac 更轻、更静，Windows 更强调边框、层级和基底

## 设计结论

### 1. 品牌基调

统一主题基调定为：

- 主品牌色：深红铜
- 深色主背景：深石墨黑
- 浅色主背景：瓷白灰
- 辅助科技色：低占比冷青绿，仅用于极少量状态和数据亮点

这意味着：

- 主色不再使用默认蓝
- 红铜是品牌识别，不是全站大面积背景色
- 科技感来自“克制高光 + 精细材质 + 准确层级”，不是靠把主色改成霓虹蓝
- 浅色主题也必须保持桌面感，不退回暖米色或通用白底蓝按钮

#### 1.1 品牌色使用预算

这轮复盘后确认，`深红铜` 不能只定义“是什么颜色”，还必须定义“出现多少”：

- 品牌色只服务于品牌识别、主按钮、焦点态、当前激活态、关键状态点
- 大面积背景、整栏底色、常规卡片底色禁止直接使用品牌色
- 单个页面中，品牌高显色面积应控制在视觉主区的 `10%` 以内
- 如果一个页面看起来“到处都是铜红”，说明设计已经偏离目标

#### 1.2 浅色主题正式约束

浅色主题在本轮复盘后不再只是“深色的补充”，而是正式设计目标：

- 主基底使用瓷白灰、冷白灰、浅石墨灰，不保留暖米色主基底
- 卡片、输入区、侧栏、工具栏必须靠明度差和边界建立层级，不能靠暖色大底制造气氛
- 浅色主题必须避免“白底 + 蓝主按钮 + 灰分割线”的通用 SaaS 组合
- 深浅两套都必须保留同一个品牌气质，而不是深色成熟、浅色又退回普通 web 产品

### 2. 全局视觉原则

#### 2.1 更像桌面应用，不像 AI 网站

- 背景要有稳定基底，不能整页漂浮
- 面板边界要真实可感知，但不要厚重描边
- 标题区、侧栏、输入区、工作区的层级必须清晰
- 页面之间的风格差异要收敛，不能每个页面一套小宇宙

#### 2.1.1 先像应用壳层，再像页面内容

本轮复盘确认，桌面感首先来自“应用外壳”，而不是来自卡片配色：

- `TitleBar / Sidebar / Toolbar / Workspace` 必须先形成统一的桌面外壳
- 页面内容层只能在这个壳层内表达差异，不能反过来压过应用外壳
- 如果首页、频道页、设置页像三个不同网站，即使颜色统一，也不算成功

#### 2.2 科技感必须克制

- 允许少量铜红高光、微发光按钮、状态光圈
- 不允许大面积彩虹渐变、蓝紫主色、强玻璃拟态泛滥
- 动效优先做呼吸、浮起、聚焦，不做跳闪和过度脉冲

#### 2.3 统一品牌主题，轻度平台适配

- mac：
  - 背景和面板更轻，更多依赖透明度和材质感
  - 边框更弱，hover 更柔和
  - 阴影更短、更糯，不要显得厚
- Windows：
  - 面板边界更清晰
  - 对比度略高
  - 侧栏、输入区、工作区分层更明确

平台适配只能是 overlay，不允许长出两套独立设计语言。

#### 2.4 可访问性与动效红线

这轮复盘后新增以下硬约束：

- 所有关键文本、输入框、边界、焦点态都必须满足桌面工作场景下的可辨识度
- 所有呼吸、浮起、发光类动效都必须支持 `prefers-reduced-motion`
- 动效只能辅助层级与状态，不得成为吸引注意力的主角
- Windows 下高对比度观感必须可用，不能依赖极弱边框勉强成立

### 3. 主题 Token 体系

建议将现有 `globals.css` 的基础 token 重构为以下层次：

要求：

- 深浅主题必须共用同一套语义 token 命名
- 不能为浅色主题单独发明另一套组件规则
- 浅色只在具体值上切换，不在结构上分叉

#### 3.1 核心语义色

- `background`
- `foreground`
- `primary`
- `primary-foreground`
- `secondary`
- `secondary-foreground`
- `muted`
- `muted-foreground`
- `accent`
- `accent-foreground`
- `destructive`
- `destructive-foreground`
- `border`
- `input`
- `ring`

其中：

- `primary` 对应品牌深红铜
- `accent` 不再和 `primary` 等价，应更偏交互 hover / 选中 surface

#### 3.2 桌面主题扩展 token

- `surface-base`
- `surface-elevated`
- `surface-panel`
- `surface-hover`
- `surface-active`
- `chrome`
- `chrome-strong`
- `chrome-divider`
- `border-subtle`
- `border-strong`
- `glow-brand`
- `glow-focus`
- `shadow-sm`
- `shadow-md`
- `shadow-lg`
- `motion-fast`
- `motion-base`
- `motion-slow`

这批 token 应成为页面和组件复用的核心，不再让页面自己发明面板色。

#### 3.3 状态色

- `success`
- `warning`
- `danger`
- `info`
- `runtime`

要求：

- 状态色都要压低饱和度
- 用于桌面应用状态表达，不做网页通知风
- 已连接、未连接、运行时未就绪、错误、进行中要有清晰但不刺眼的视觉差异

### 4. 组件层规则

本轮复盘确认，第一波不能只改页面壳层，必须同时纳入共享 primitive：

- `Button`
- `Input`
- `Textarea`
- `Select`
- `Tabs`
- `Badge`
- `Card`
- `Switch`

#### 4.1 Sidebar / 应用外壳

- Sidebar 不再是普通浅色栏，而是桌面应用外壳的一部分
- 应更接近“轻材质 + 低对比 + 稳定边界”
- 搜索框、分组标题、品牌区、底部账户区要共享统一 surface 规则

#### 4.2 页面工作区

- 页面主区背景不要纯白平铺
- 卡片不应像网页营销区块，需更像桌面工作台面板
- `WorkspacePage` 应承担全局页面节奏，不允许某个页面自己重新定义一套背景逻辑

#### 4.3 输入与按钮

- 输入框应更像桌面输入容器：边界清晰、聚焦准确、默认状态安静
- 主要按钮允许带轻微铜红高光
- 次级按钮保持低调，不能把所有按钮刷成品牌色
- 所有共享控件必须优先吃 token，不允许继续依赖 shadcn 默认语义表现
- `Select / Input / Button` 必须先统一，否则页面再漂亮也会被旧控件拉回 web 风

#### 4.4 状态点与徽标

- 状态类表达允许柔和微动效
- 默认点、禁用点、连接点、异常点都要共享规则
- 不能再每个页面单独决定颜色和动画

### 5. 页面落地优先级

第一批优先收敛：

- 全局 token 与 `globals.css`
- `MainLayout / Sidebar / TitleBar`
- `Chat` 首页
- `Channels`

第二批再进入：

- `Agents`
- `Skills`
- `Settings`
- `Dashboard / Models / Cron`

### 6. 技术落地约束

- 主题重构必须先改 token，再改组件，再改页面，不允许反过来
- 禁止在页面里继续写固定 hex 作为长期方案
- 新增视觉语义必须优先进入共享样式层
- 平台差异只允许存在于壳层、滚动条、边框强度、材质强度，不允许复制两套组件
- 任何新的品牌 glow、透明度和阴影都必须先经过深浅双端校验，再进入共享样式
- 首页插画和功能卡片如果明显拖后腿，允许在试点阶段替换，但不能让插画资产反向绑架主题系统

### 7. 开发闭环准则

这次暴露出来的问题说明，主题文档不仅要约束视觉，也要约束开发流程本身。后续所有相关工作必须遵守以下硬规则：

- 只能把 `/Users/jianglong/workspace/XClaw` 作为唯一工作树，不能把旁路备份目录、临时目录或其他仓库视作有效修改对象
- 每次声称“闭环”“完成”“已修复”之前，必须同时核对 `provider store`、`~/.openclaw/openclaw.json`、`CLI/runtime`、`UI` 四层是否一致
- 只能修搜索或 UI 作为表层现象，不允许用局部界面改动掩盖 `runtime` 身份错误、配置漂移或 provider 同步失败
- 只有当工作树与运行树一致时，才允许宣称完成；如果两者不一致，任何验收结论都不成立
- 若四层核对里有任一层不一致，必须先修正身份与配置链路，再讨论 UI 呈现或搜索结果
- 这类问题的判断标准必须以真实运行证据为准，不允许凭页面视觉“看起来正常”就下结论
- 任何涉及 `provider`、`runtimeKey`、`model ref` 的修改，都必须额外核对这四件事是否同一套事实：`provider store`、`~/.openclaw/openclaw.json`、`openclaw models list`、聊天模型选择器
- 这类问题的测试口径必须与真实 UI 口径一致：展示层看 `label/hint`，运行层看 `qualified ref`，禁止再用旧的全量 ref 文本去断言新的 UI 展示
- `takeover reconciler` 这类启动同步链只能按 `runtime provider key` 合并已有 richer account，不能再用 runtime 的降维视图直接整库覆盖 `provider store`
- 小的、低风险、局部 UI 微交互允许敏捷直改，不强制每次都走红绿测试；但这条例外只适用于不触碰协议、状态链、滚动契约和跨组件数据流的改动，仍需做最小静态校验或直接目视验证

## 三轮复盘结论

### 第一轮：品牌方向复盘

结论：

- `深红铜 + 石墨黑 / 瓷白灰` 的大方向正确
- 但如果不限制品牌色预算，后续实现很容易再次滑向“炫但土”的假科技感

本轮收口：

- 品牌色使用预算正式写入设计稿
- 浅色主题从“示意”提升为正式目标

### 第二轮：系统结构复盘

结论：

- 只定义背景和主色还不够，真正决定桌面感的是“应用外壳 / surface / primitive”
- 如果不把共享控件纳入第一波，页面试点最终会被旧输入框和旧按钮拖回 web 风

本轮收口：

- 增加 `chrome-divider / motion-*` 等扩展 token
- 明确第一波纳入共享 primitive

### 第三轮：交付风险复盘

结论：

- 当前最大风险不是方向错，而是实现时再次“局部漂亮、全局失控”
- 尤其要防止浅色回暖、深色 glow 过重、mac / Windows 平台适配失控

本轮收口：

- 新增可访问性、动效、双端校验约束
- 明确平台差异和插画资产都不能凌驾于主题系统之上

## 待定设计项

- 是否保留“暖色浅色主题”作为兼容分支，还是直接切到新的浅色石墨体系
- 深色主题下铜红 glow 的强度是否需要再压低一档
- 标题栏区域是否需要更明确地做出 mac / Windows 的轻度视觉差异
