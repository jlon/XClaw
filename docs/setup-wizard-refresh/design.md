# Setup 引导页重构设计

## 背景

当前 `Setup` 页虽然已经完成了主题表层收口，不再使用旧的暖色大底和默认蓝面板，但它的结构仍然不是标准桌面引导页：

- 步骤骨架不稳定，`takeover` 路径会退化成只有 1 到 2 步的半流程
- 单页内容承载过多职责，`Runtime` 和 `Provider` 都更像设置页，而不是引导页
- 页面外层仍是“一个大卡片 + 内部条件切换”，没有形成标准桌面向导的固定壳层
- `Setup` 文件本身过大，信息架构和交互状态耦合在一个文件里，后续很难稳住质量

这不只是视觉问题，而是信息架构和任务流问题。要让它在 mac / Windows 上都像一个成熟的桌面应用引导页，必须把结构重新设计。

## 目标

- 将 `Setup` 重构成标准桌面向导，而不是“设置页内容搬进一个大卡片”
- 在 mac / Windows 上都保持统一品牌主题，并符合桌面引导页的稳定、克制、低噪音特征
- 让用户按“开始方式 -> 环境准备 -> 模型接入 -> 完成确认”的任务流完成首次使用
- 让 `fresh` 和 `takeover` 两条路径共用同一套骨架，不再长出两种不同的向导结构
- 将现有单文件拆成更清晰的壳层组件和阶段组件，降低后续回归风险

## 非目标

- 不把 `Setup` 做成营销落地页或大插画欢迎页
- 不为 mac / Windows 设计两套完全不同的引导页
- 不在本轮重做所有 provider 逻辑或 runtime 业务逻辑
- 不在本轮引入复杂动画、全屏视频、夸张渐变背景

## 设计结论

### 1. 统一骨架，但不强迫两条路径做同样动作

`Setup` 统一收敛成 4 个阶段语义，但 `fresh` 和 `takeover` 不必执行完全相同的人工动作：

1. `开始`
2. `准备`
3. `模型与接入`
4. `完成`

这样可以保证：

- 用户始终知道自己在流程中的位置
- `takeover` 不再看起来像一个“做完就消失”的半流程
- 页面不会因为条件分支不同而变成完全不同的产品体验
- `takeover` 可以在“模型与接入”阶段直接进入“复用已有接入”的确认态，而不是强迫用户重新填写一遍所有字段

### 2. 标准桌面向导布局

采用“左侧被动步骤轨 + 右侧内容区 + 底部固定操作栏”的标准桌面向导布局。

#### 2.1 左侧被动步骤轨

- 固定宽度，展示 4 个阶段
- 展示当前步骤、已完成步骤、未开始步骤
- 只负责导航和状态表达，不承载正文说明
- `takeover` / `fresh` 不改变导航数量
- v1 默认不可直接点击跳转，避免跨阶段跳步导致状态不一致
- 视觉上更接近轻量向导进度轨，而不是设置中心 tab 栏

#### 2.2 右侧内容区

- 只展示当前阶段内容
- 内容区允许根据阶段类型改变密度，但不允许每一步都变成整页不同布局
- 正文说明、字段区、状态区、警告区都在同一视觉节奏下组织

#### 2.3 底部固定操作栏

- 左侧：返回
- 右侧：次级动作、主动作
- 所有步骤都共享同一个操作栏位置
- `Installing` 阶段也保留底部区，但只展示只读进度和受控动作
- 主要阶段切换一律通过底部操作栏完成，不依赖左侧步骤导航点击

#### 2.4 动作契约

桌面向导不是只有按钮位置，还必须有稳定动作语义：

- `开始`：
  - 次级动作：退出引导
  - 主动作：继续
- `准备`：
  - 次级动作：返回
  - 主动作：继续
- `模型与接入`：
  - 次级动作：返回
  - 主动作：保存并继续 / 复用并继续
- `完成.applying`：
  - 不提供跳步动作
  - 关闭窗口需要二次确认
- `完成.summary`：
  - 主动作：进入 XClaw

约束：

- v1 移除当前全局 `Skip Setup` 语义，不允许中途直接把 setup 标记完成
- 完成前关闭窗口，等价于中断引导，不写入 `setupComplete`
- 只有最终完成按钮允许触发真正的激活与落盘

### 3. 四阶段详细定义

#### 3.1 开始

目标：让用户选清楚“接管现有 OpenClaw”还是“全新开始”。

内容：

- 欢迎说明
- 如果检测到现有 OpenClaw，则显示接管提示和当前环境摘要
- 两张选择卡：
  - 接管现有环境
  - 全新开始
- 一段简短解释当前推荐项为什么是推荐项

规则：

- 这一步不执行重操作
- 只做路径选择和基础认知建立
- 不在本步塞入 provider、runtime、日志

#### 3.2 准备

目标：把环境准备和系统检查做成一页清晰的“就绪确认”，而不是工程师诊断台。

内容：

- `fresh` 路径：
  - 工作目录
  - Gateway 端口
  - 环境检查摘要
- `takeover` 路径：
  - 导入将影响什么
  - 已识别的 provider / skill / extension 概览
  - 冲突与警告
- `takeover` 的真正导入动作在本阶段尾部触发，而不是在“开始”阶段触发
- 高级区折叠：
  - 日志查看
  - 重试检查
  - 详细诊断信息

规则：

- 默认只展示用户需要决策的内容
- 日志、长错误、技术细节全部进入折叠高级区
- 不在主区直接堆一长列工程状态卡

#### 3.3 模型与接入

目标：让用户完成“模型接入”这件事，而不是进入一个迷你的设置页。

内容：

- Provider 选择器
- 该 provider 对应的必要字段
- OAuth 与 API Key 二选一时，优先显示推荐接入方式
- 若为 `takeover` 且已有可用 provider，则默认进入“复用现有账号”摘要态
- 若 `takeover` 导入后不需要人工 review，本阶段直接显示“已复用接入配置”的确认态，而不是强制用户重新配置

规则：

- 先选 provider，再展开字段
- OAuth、API Key、Custom 协议不同时大面积展开
- `Custom` 仍保留，但明确放在次级路径
- 成功状态和校验结果要靠近主 CTA，不要散落在页面底部
- 页面内部也必须单任务化：
  - 先决定“用哪种接入方式”
  - 再展示该方式对应的必要字段
  - 不允许把 provider 列表、OAuth、API Key、custom 协议和长帮助同时堆满首屏

#### 3.4 完成

目标：给用户明确的完成感和启动前确认，而不是“点完就直接进入首页”。

内容：

- 应用变更中的最终进度
- 当前采用的接入方式
- 默认 provider / account
- runtime / gateway 是否就绪
- 已启用的基础能力摘要
- 进入应用的主按钮

规则：

- 无论 `fresh` 还是 `takeover`，都必须经过完成页
- `takeover` 不再导入完成后直接结束流程
- 完成页不放复杂设置项，只给摘要和下一步
- `完成` 阶段分为两个子状态：
  - `应用变更中`：执行技能安装、最终写入、必要的收尾任务
  - `已完成`：展示摘要并允许进入应用
- 左侧步骤导航在这两个子状态下都停留在 `完成`

### 3.5 激活时机

`Setup` 的最终激活时机必须写死，不能边做边决定：

- `takeover` 导入、provider 校验、runtime 检查都只是在准备 setup 状态
- `markSetupComplete` 与 `completeSetupSession` 只能发生在 `完成.summary` 的最终主按钮
- 任何路径都不允许在中途绕过完成页直接进入首页
- 如果 `takeover` 已完成导入，也只意味着可以进入完成阶段，不意味着整个引导已结束

## 交互原则

### 1. 单步单职责

每一步只解决一个主要问题：

- 开始：怎么开始
- 准备：环境准备好没有
- 模型与接入：用什么模型、怎么接入
- 完成：确认并进入

如果一页里同时要求用户做“读说明、改路径、看诊断、配 API、处理 OAuth、看日志”，就说明这一步设计失败。

### 2. 默认主路径优先

- `fresh` 用户的最短路径必须明显可走通
- `takeover` 用户的推荐路径必须清楚且低噪音
- 自定义 API、手动 code、日志等都属于次级路径

### 2.1 回看可以，跳步不行

- 用户可以通过底部 `返回` 回看前一阶段
- v1 不支持从左侧步骤导航直接跳到任意阶段
- 这样可以避免 provider、runtime、takeover 状态流在尚未准备好时被提前访问

### 2.2 不再保留全局跳过

- 当前 `Skip Setup` 会直接破坏完成感和 setup 完整性
- v1 不提供“全局跳过并标记完成”
- 如果未来需要“稍后再做”，它也必须是“退出引导但不写入完成状态”，而不是当前的直通完成

### 3. 高级信息折叠

以下内容默认不进入主阅读流：

- 长日志
- 长错误详情
- provider 文档外链集合
- OAuth 手动 code 兜底说明
- runtime 技术诊断细节

它们都应进入折叠高级区或条件显示区。

## 视觉原则

### 1. 应用外壳优先

- `Setup` 仍属于 XClaw 应用内流程，不是独立品牌落地页
- 继续使用全局桌面主题 token
- 左导航、右内容、底部操作栏共享应用外壳语言

### 2. 内容密度分级

- 欢迎 / 完成：更宽松
- 准备 / 模型与接入：更紧凑
- 不允许全部步骤都用同一种大卡片密度硬撑

### 3. 平台差异

- mac：更轻、更静，边框更弱
- Windows：边界更清晰，内容区与导航区分层更强

差异只来自 overlay，不拆两套设计。

## 组件边界

当前 `src/pages/Setup/index.tsx` 过大，本轮重构必须拆分。

建议最少拆成：

- `SetupShell`
- `SetupStepRail`
- `SetupFooter`
- `SetupStartStage`
- `SetupPreparationStage`
- `SetupProviderStage`
- `SetupCompleteStage`

辅助块可继续拆：

- `TakeoverModeCard`
- `RuntimeChecklist`
- `ProviderOAuthPanel`
- `SetupSummaryCard`

要求：

- 壳层负责布局与步骤状态
- 阶段组件负责单步内容
- 与 host / gateway / provider 的状态流仍由页面容器统一编排

## 实施边界

- 不改已有 setup 后端协议
- 不改已有 provider 保存逻辑
- 不改 gateway 启动策略
- 允许重排步骤、重组内容和重写前端组件边界
- 允许把 `takeover provider review` 合并进“模型与接入”阶段，而不是保留独立主步骤

## 完成标准

满足以下条件后，`Setup` 才能算完成：

- `fresh` 和 `takeover` 共用同一套四阶段骨架
- 任何路径都必须经过完成页
- 主区不再出现设置页式巨型混合表单
- 日志和高级诊断已折叠到次级路径
- 页面结构在 mac / Windows 上都像标准桌面引导页
- `Setup` 从单文件拆成清晰组件边界
